# Dashboard and analysis: security review

Scope: `dashboard/**`, `insights/metrics.py`, `insights/classify.py`, `insights/pipeline.py`, `insights/topics.py`,
`.streamlit/config.toml`. The scraper, parser and store are reviewed separately.

Threat model: anyone can write a Booking.com review, so review text, reply text, room type, country, property
slug, topic evidence and even `scrape_runs.error` are **untrusted**. The readers are hotel ops staff. The database
file path comes from `REVIEWS_DB` (operator controlled, but still never trusted to be well formed).
Method: every finding has an exploit test in `tests/test_security_dashboard.py`, written to fail first, then fixed.

## What changed that other modules might notice

* `insights.metrics`: new `safe_label()`, `MAX_TREND_WEEKS`, `MAX_NAME_CHARS`. `weekly_trend()` signature and columns are the same, but it returns at most 520 weeks. `_read()` now re-raises database errors other than "no such table / column". `load_reviews()` turns impossible dates into NaT. Unknown property slugs display as sanitised names.
* `insights.classify`: new `normalise()`, `MAX_TEXT_CHARS`, `MAX_EVIDENCE_CHARS`, `CLASSIFIER_REVISION`. `TopicTag.evidence` is the normalised sentence, cut to 300 characters, not the byte-exact original.
* `insights.pipeline`: `review_topics_state.taxonomy_version` now holds `"<TAXONOMY_VERSION>+<CLASSIFIER_REVISION>"`. `review_topics.taxonomy_version` is unchanged (`"1"`). The first run after this change re-tags every review once.
* `dashboard.ui.data`: `feed_to_csv()` keeps its signature. New `feed_to_csv_limited()`, `MAX_EXPORT_ROWS`, `MAX_SEARCH_CHARS`, `clean_reviews()`, `clean_topics()`, `clamp_page()`, `parse_topic_choice()`. New `dashboard/ui/privacy.py`.

## Residual risks (accepted, with reason)

* **No authentication.** Streamlit has none. Anyone who can reach the port can read every review. Run behind a reverse proxy or VPN with sign-in and TLS, or bind to localhost (`--server.address 127.0.0.1`). This file does not set an address because it would break LAN use.
* **Config is read from the folder Streamlit starts in.** Start it from the project root, or the hardening silently does not apply.
* **PII masking is best effort.** Spelled-out emails or numbers ("john at gmail dot com" written as words, digits as words), and digit groups of 8 to 15 digits that are not phone numbers (masked as a false positive, the safe direction) cannot be separated perfectly. Names and street addresses typed by guests are not detected.
* **Searching by a name fragment can still hit text that is masked on screen** (for example `john` matches `john@x.com`). Searches that look like a whole email or phone number are refused. Fragment matching was left alone as a usability trade-off.
* **CSV apostrophe.** Text that starts with `=`, `+`, `-` or `@` gets a leading apostrophe in the export (OWASP advice). A review that legitimately starts with "- great" shows the apostrophe in Excel. Cells longer than 30,000 characters are cut.
* **Classifier reads only the first 5,000 characters.** A complaint after that point is ignored. Real Booking.com reviews are far shorter.
* **Look-alike mapping is a short table.** Rare confusables outside it (for example some mathematical alphabets are handled by NFKC, but not every Cyrillic or Georgian shape) can still evade the keyword match.
* **Large databases are slowish.** 200,000 reviews take 3 to 6 seconds per interaction. Acceptable for a Monday-morning tool, not for hundreds of concurrent users.
* **A hostile row is skipped, not repaired.** If someone injects many rows with dates in the future, the page reports "N reviews skipped" but the real fix belongs on the scraper side (validate before storing).
* **Browser rendering was not tested.** The tests prove what the server emits (no live tags, attributes, links or images). They cannot prove how a given browser treats it, which is why the output is escaped at several layers.
