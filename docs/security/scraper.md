# Security review: collection side (`scraper/`)

White-box review of our own code. Threat model: **the remote server (Booking.com, or anything that can answer
in its place) is untrusted**; the operator running the CLI is trusted but can make typos. Every finding below has
an exploit test in `tests/test_security_scraper.py` (written first, seen failing, then fixed). Tests that passed
on first run are kept as regression guards and marked "already safe".

Rules of engagement: local fixtures and `tmp_path` databases only, no network, no real browser, `data/*.db` never touched.

## Contract notes (other modules)

- `reviews` primary key unchanged (`review_key`), because `review_topics` and the dashboard join on it alone. Cross-property reuse is rejected instead.
- `Review`/`ParsedPage` fields unchanged. Values are now validated (key and slug patterns, date window, nights, votes) and text is sanitised/truncated. `host_reply` is NULL when blank after cleaning.
- `UpsertResult` gained `conflicts` (default 0). `ReviewStore` gained `close()` and `busy_timeout_s`; `finish_run` raises `ValueError` for unknown status; store methods raise `StoreError` instead of raw `sqlite3` errors.
- `scrape_runs.rejected` now includes cross-property conflicts; quarantine keeps at most 50 rows per page.

## Residual risks

1. **Stored text is untrusted at render time.** `host_reply` is HTML-unescaped by design, so it can contain literal `<script>`/markdown/links. Collection strips control characters but does not HTML-escape (that would corrupt data). The dashboard must escape on output and never use `unsafe_allow_html` with review text.
2. **A malicious server can still lie plausibly**: fake but well-formed reviews, an all-known first page that stops an incremental run early, or a low `reportedTotal`. Nothing local can verify truth.
3. **Response body is fully downloaded** before the size check (Playwright limitation); the 5 MB cap protects parsing and storage, not bandwidth or memory for that one response.
4. **No request blocking inside the page**: Booking legitimately loads third-party scripts, so only the top-level URL and the review-data origin are enforced.
5. **`--db` may point anywhere writable** (path traversal is the operator's own choice); only silent-data-loss forms are refused.
6. **Existing database rows** written before this hardening are not re-validated.
7. Rows in `quarantine` and `scrape_runs.error` are shown to staff by the dashboard; they are now cleaned at the source, but the dashboard should still escape them.
